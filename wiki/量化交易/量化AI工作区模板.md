> 量化场景的文件结构首先是风控结构。目录怎么分，不是为了好看，而是为了让研究、回测、执行、审计彼此隔离，避免一个 agent 同时研究、下单、给自己做风控，最后谁也说不清哪里出了问题。

## 背景与动机

- 一人公司做量化最容易踩的坑，不是模型不会分析，而是把研究、执行和风控混成一团。
- 一旦回测被覆盖、审计和执行共用状态，实盘出问题后就无法复盘“当时为什么这样做”。
- 白皮书因此把量化场景明确写成分轨结构，本质上是在用文件系统实现风控边界。

## 核心内容

### 推荐目录骨架

```text
量化工作区/
├── 00-数据/          # raw / factors / alt-data
├── 10-策略/          # research / alpha / portfolio / risk
├── 20-回测/<run-id>/ # 每次回测独立 run
├── 30-执行/          # orders / positions / execution-rules.md
├── 40-复盘/          # daily / weekly / postmortem
├── 90-合规审计/      # audit-log.jsonl 仅追加
└── .claude/agents/   # researcher / trader / risk-officer / auditor
```

### 这套结构真正解决什么问题

- `00-数据/` 把原始数据与因子、替代数据分开，避免后续研究改写原始事实。
- `10-策略/` 把研究逻辑、alpha、组合和风险判断放在策略层，而不是跟执行日志混杂。
- `20-回测/<run-id>/` 强制每次实验保留独立快照，防止“上一次为什么赚钱/亏钱”被覆盖掉。
- `30-执行/` 只放真实执行相关状态，让研究和实盘之间的边界可追踪。
- `90-合规审计/` 保证关键操作有 append-only 留痕，方便后续对账与风控复盘。

### 这一场景最关键的治理动作

- 研究、执行、风控、审计角色必须分离。
- auditor 不应读取 trader 的可变状态，只应读取审计日志。
- 回测目录必须按 run 分开，不能让新结果覆盖旧结果。
- 这些动作不是“规范建议”，而是量化场景能否被称为系统的最低条件。

### 最常见的反模式

- 一个 agent 同时研究、执行、风控，最终没有任何防火墙。
- 回测结果持续覆盖，导致策略演化没有可追溯历史。
- 把风险判断写在聊天记录里，而不是策略或审计文件里，导致后续根本无法重建决策链。

### 更适合沉淀成 agent 的能力

- researcher: 做因子研究、市场观察、策略草案。
- trader: 执行具体下单与仓位调整动作。
- risk-officer: 读取风控规则与仓位暴露，给出阻断或预警。
- auditor: 只读日志，做独立审计与异常解释。

## 现状与趋势

- 越来越多量化 agent 框架开始强调 checkpoint、持久化日志和角色分工，而不是单一大模型直接做全流程。
- 这说明量化场景里，文件树和日志树的重要性不会下降，反而会成为 AI 化是否可信的核心指标。
- 对一人公司来说，最现实的收益不是“自动暴富”，而是把研究与执行过程变得更稳定、更可解释。

## 开放问题

- 当策略数量变多时，回测 run 的索引、归档和检索是否需要再升级成更强的实验管理层。
- 风控 agent 的边界到底应以文件权限还是执行网关来兜底，仍需结合实盘工具链判断。
- 如果后续把量化子树进一步并入已有量化知识库，哪些目录该留在 `OPC`，哪些该迁入量化主树，还需要再整理。
